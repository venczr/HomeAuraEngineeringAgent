3. CORRECTED FUTURE OFFLINE REWRITE DESIGN
==========================================

Why the previous template was unsafe:

git filter-repo --refs refs/heads/feature/room-geometry ...

implies --partial. Partial mode can retain old local refs, remote-tracking refs
and reflogs. In the current repository that would leave local main and
refs/remotes/origin/feature/room-geometry capable of recontaminating the remote.

Selected future design, not executed:

1. Freeze all repository writers and complete the backup gates in section 6.
2. Create an offline branch-only Git bundle from the verified remote branch
   SHA. The bundle is a Git-object/ref carrier only; it does not contain LFS
   payloads.
3. Make a fresh disposable bare clone from that branch-only bundle, explicitly
   selecting feature/room-geometry, then remove the clone's origin configuration.
   A bundle is not an on-disk Git repository and cannot hardlink repository
   objects, so --no-local is not applicable to this clone. If an on-disk Git
   repository is ever substituted as the clone source, --no-local is mandatory.
   A bare clone does not create normal branch reflogs by default; verify this
   rather than assume it.
4. Verify in the disposable source:
   - exactly one ref exists;
   - it is refs/heads/feature/room-geometry;
   - it equals c11205f9a4f8379d2f2cbd7a9bd38013bf0e4db7;
   - no main, refs/remotes/*, tags, replace refs, notes, stash or reflogs exist;
   - no remote is configured;
   - commit count is 16;
   - both known LFS pointer OIDs equal the values in section 2.
5. Create a separate empty disposable bare target repository outside the live
   repository and outside the backup.
6. Set GIT_LFS_SKIP_SMUDGE=1 and keep GIT_TERMINAL_PROMPT=0 for the rewrite.
   The disposable repositories have no GitHub remote, so they cannot contact or
   push to GitHub.
7. Run git-filter-repo with alternate source and target. Alternate source/target
   implies partial processing internally, but the manual explicitly distinguishes
   this case: old and new histories are in separate repositories, so they cannot
   mix. All refs present in the sole-ref disposable source are processed. No
   --refs option is used.

Exact future command template, one line, DO NOT RUN:

git filter-repo --source "<DISPOSABLE_SOURCE_BARE>" --target "<DISPOSABLE_TARGET_BARE>" --sensitive-data-removal --no-fetch --invert-paths --path "projects/Test_01/HomeAura_Test_01.mrd" --path "projects/Test_01/Test_01.dwg" --path "projects/Test_01/Test_01.bak" --path "evidence/ops1/HOMEAURA-OPS1-IMPLEMENT-20260727-014945/" --path "reports/HomeAura_OPS1_Implementation_Report_2026-07-27.txt" --path "reports/HomeAura_OPS1_Implementation_Report_2026-07-27.txt.sha256"

--no-fetch is explicit. With --sensitive-data-removal, filter-repo normally
gathers refs. The explicit option prevents that behavior. Its missed-ref risk is
bounded by:

- the successful live remote inventory immediately before the freeze;
- the branch-only offline bundle;
- the exact one-ref disposable-source check;
- a second live remote inventory immediately before any future publication.

No --force is present. The separate empty target preserves the safety boundary.
If the installed filter-repo version rejects this source/target arrangement,
stop and redesign the disposable workflow; do not add --force automatically.
If a normal verification clone is later made from the local target repository,
use git clone --no-local because the source is an on-disk repository. A bundle
file itself cannot hardlink source repository objects, so --no-local is not
applicable to bundle materialization.

No GitHub remote may be added until every Gate B validation succeeds. Any future
remote update must use an exact branch refspec and a force-with-lease tied to the
last verified remote SHA, never a blind --force or an unreviewed --mirror.
