4.1 AutoCAD plugin boundary

Version:
1.2.0.0

Runtime:
.NET Framework 4.8, AutoCAD 2024 managed API.

Relevant commands:

- HA_EXPORT_MODEL:
  reads layers, entity types, entity handles, layer, extents, centers and block
  definitions, then writes model_snapshot.json beside the DWG.
- HA_SYNC_MODEL:
  sends the ModelSnapshot DTO to
  POST /api/v1/projects/{project_name}/snapshot.
- HA_DISCOVER_ROOM:
  manually inspects selected objects, attributes, dynamic/public properties,
  XData and extension dictionaries, then writes a discovery JSON.
- HA_DISCOVER_ROOM_BOUNDARIES:
  read-only boundary inventory and diagnostics.
- HA_EXPORT_ROOMS:
  exports MagiCAD room markers and selected Boundary data.
- HA_SYNC_ROOMS:
  serializes the fixed RoomExportReport C# DTO and sends it to
  POST /api/v1/projects/{project_name}/rooms.
- HA_ANALYZE_MODEL:
  requests generic snapshot analysis from the API.

The plugin has no Project, Building, Level or engineering-system domain layer.
Its project identity is inferred from the directory containing the DWG.

4.2 Snapshot contract

C# ModelSnapshot contains:

- GeneratedAtUtc;
- DrawingName and DrawingFullPath;
- AcadVersion and PluginVersion;
- process bitness and drawing units;
- drawing extents;
- ModelSpaceEntityCount;
- Layers;
- EntityTypes;
- Entities;
- BlockDefinitions.

Python agent.model_reader.ModelSnapshot models the same summary except that
Entities is not a declared field and is ignored by Pydantic. The API preserves
the raw payload separately and uses raw Entities for remote-geometry
diagnostics.

Snapshot is an inventory/diagnostic contract. It does not represent a building
hierarchy, openings, equipment connections or engineering systems.

6. KEY GAPS AND CONFLICTS
========================================================================

6.1 No authoritative hierarchy

The repository has project directories, flat Rooms[] data and optional IFC
storey evidence, but no Project -> Building -> Level -> Room hierarchy.

6.2 Identity is source-specific

AutoCAD Handles are stable only within a drawing lineage. Room.Code may be
missing or duplicated. IfcSpace.GlobalId is strong but optional and belongs to
a geometry candidate. No current value can simply become a universal domain ID
without an explicit namespace and precedence policy.

6.3 Direct rooms.json expansion is unsafe

The current API parses extra fields with extra="ignore" and serializes the known
model. A future producer could add an unknown hierarchy field that the current
POST /rooms silently discards. Therefore DOMAIN-1 must not add required domain
fields to rooms.json and must not use rooms.json as its write target.

6.4 Building and Level must not be guessed as validated

Legacy rooms contain no building or level relationship. DOMAIN-1 may use
deterministic "unassigned" containers only if source and validation status make
the absence explicit.

6.5 Geometry statuses have distinct meanings

- Boundary geometry_status=validated is an authoritative supported AutoCAD
  boundary.
- Boundary geometry_status=provisional is a planar Polyline3d fallback.
- IfcSpaceGeometry.geometry_status=validated_candidate means the IFC geometry
  passed analytic checks, not that it replaced Boundary.

A new generic validation_status must preserve these distinctions and must not
collapse validated_candidate into validated Boundary.

6.6 API and plugin are fixed legacy consumers

API version 0.6.0 and plugin 1.2.0.0 currently exchange snapshot and
RoomExportReport. Adding mandatory hierarchy fields would require synchronized
changes and break old JSON. DOMAIN-1 should have no API/plugin change.

6.7 IfcOpenShell remains optional by architecture

The current .venv happens to contain ifcopenshell 0.8.5. However:

- it is declared only in requirements-ifc.txt;
- importer loading is lazy;
- the base API imports without it;
- a test actively blocks ifcopenshell imports and proves API 0.6.0 starts.

DOMAIN-1 must not import agent.ifc_space_importer or ifcopenshell. It may depend
only on safe Pydantic contracts such as ifc_space_models if needed.

9. DOMAIN-1 CONTRACT DESIGN
========================================================================

9.1 New envelope

DomainDocument:

- schema_version: "1.0";
- project: DomainProject.

Domain output uses controlled Pydantic models with extra="forbid". Legacy input
continues to use the current tolerant RoomExportReport reader.

9.2 Entity metadata

EntitySource:

- kind;
- source_id;
- source_version, optional;
- source_context, optional and path-free.

ValidationStatus enum:

- validated;
- provisional;
- requires_confirmation;
- invalid;
- missing.

Every Project, Building, Level, Room and Boundary has:

- stable_id;
- source;
- validation_status.

9.3 Stable ID policy

Use a fixed documented UUIDv5 namespace and canonical path-free keys.

Precedence:

1. Preserve an explicit future domain stable_id if supplied by the domain
   contract itself.
2. Project:
   UUIDv5("project/{normalized project_id}").
3. Legacy room:
   UUIDv5("room/{project stable id}/{normalized DrawingName}/
   {SourceHandle}").
4. Boundary:
   UUIDv5("boundary/{room stable id}/{Boundary.SourceHandle}").
5. If SourceHandle is missing, a Code-based fallback may be generated only with
   validation_status=requires_confirmation and a diagnostic; duplicate
   fallbacks must be rejected as ambiguous.

Do not use DrawingFullPath in identifiers or output.
Do not replace a room stable_id when IfcSpace.GlobalId later appears.
Store IfcSpace.GlobalId as source evidence/alias, not as a reason to renumber an
existing domain room.

9.4 Legacy Building/Level behavior

Legacy rooms have no authoritative Building or Level.

The adapter creates deterministic containers:

- Building name/key: unassigned;
- Level name/key: unassigned.

Both must use:

- source.kind = legacy_placeholder;
- validation_status = requires_confirmation;
- a diagnostic explaining the missing source relationship.

They must never be labeled validated.

9.5 Room/Boundary wrapping

DomainRoom preserves:

- Code and Name;
- source marker Handle;
- existing MagiCAD scalar data as source data;
- optional Boundary;
- optional IfcSpaceGeometry candidate.

DomainBoundary wraps the existing typed RoomBoundary without recalculation.

Mapping:

- current validated LWPOLYLINE -> validation_status=validated;
- current provisional Polyline3d -> validation_status=provisional;
- current missing/ambiguous -> missing or requires_confirmation;
- IfcSpace validated_candidate remains a separate candidate field and never
  overwrites Boundary.

9.6 Additive optional strategy

- Do not add fields to legacy rooms.json in DOMAIN-1.
- Do not write a migrated JSON file.
- Do not add an API route.
- Do not change API version 0.6.0.
- Do not change AutoCAD DTOs.
- Adapter input is project_id plus existing RoomExportReport/raw legacy payload.
- Adapter output exists only in memory and test serialization.
- All missing hierarchy metadata is optional or represented by explicit
  requires_confirmation placeholders.

========================================================================
10. DOMAIN-1 MIGRATION STRATEGY
========================================================================

DOMAIN-1 migration is a lazy read adapter, not an in-place migration.

Rules:

1. Read rooms format 1.0 and 1.1 with current RoomExportReport.
2. Never rewrite the source file.
3. Build DomainDocument in memory.
4. Preserve Boundary data exactly.
5. Preserve IfcSpaceGeometry as a candidate exactly.
6. Emit schema_version="1.0" only in the new domain envelope.
7. No field in existing rooms.json becomes newly required.
8. Unknown future legacy major versions fail with a controlled message; known
   1.0/1.1 remain accepted.
9. Missing building/level data is explicit and requires confirmation.
10. Repeated mapping of identical input produces identical stable IDs and
    semantically identical domain JSON.

No rollback is needed because DOMAIN-1 has no persistence side effect.
