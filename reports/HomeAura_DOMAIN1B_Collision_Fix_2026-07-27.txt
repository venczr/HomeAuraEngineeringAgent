4. PREVIOUS COLLISION CAUSE
========================================================================

The collision-safe JSON UUID helper from DOMAIN-1A was correct. The
remaining defect happened before that helper.

The old identity preparation behavior was:

1. Detect an absolute path.
2. Reduce it to the final basename.
3. Canonicalize that basename.
4. Use it as a UUID component.

Therefore two different inputs such as synthetic audit paths on
different drives but with the same final name became the same UUID
component.

The old Mapping-key behavior was:

1. Detect an unsafe key.
2. Replace every unsafe key with the same literal redacted key.
3. Assign values into a Python dict.

Two distinct keys therefore targeted the same output key, and the
second assignment silently replaced the first value.

canonicalization and UUID generation.

- Room.Boundary.SourceHandle

Rejected forms:

- UNC path

- Windows device path with dot prefix
- POSIX absolute path
- local file URI
- server file URI

Message and diagnostics contain only:

- the safe code
- the fixed identity field name

They never contain:

- the input value
- a parent directory
- a drive
- a server/share
- the basename from the rejected path

The rejected input Mapping remains unchanged.

No basename reduction or path hashing is performed for identity fields.

7. SAFE MAPPING-KEY EXCLUSION
========================================================================

Recursive portable Mapping handling now works as follows:

1. Convert a candidate key to text for inspection.
2. If the key is an absolute path or file URI, skip the entire entry.
3. Do not emit a replacement key.
4. Do not recurse into or retain a partial value from that entry.
5. Count excluded entries at the current Mapping.
6. Emit one non-disclosing diagnostic for that Mapping:

unsafe_mapping_key_excluded location={safe structural location};
removed_count={exact count}

Safe siblings remain unchanged.
Nested mappings use the same logic recursively.
The input Mapping remains unchanged.

The permanent test contains:

- two unsafe root keys with the same basename;
- one safe root key;
- a safe key whose literal value is
  <absolute_field_name_redacted>;
- a nested Mapping with two unsafe keys;
- one safe nested key.

Observed output:

- both unsafe root entries excluded;
- both unsafe nested entries excluded;
- safe root entry preserved;
- literal placeholder-named safe entry preserved;
- safe nested entry preserved;
- root diagnostic removed_count is 2;
- nested diagnostic removed_count is 2;
- no unsafe source key appears in output or diagnostics;
- no value overwrote another value.

There is one literal placeholder occurrence remaining in the adapter's
unknown-field diagnostic display helper. It does not create or mutate a
portable Mapping key. The regression test proves a real safe Mapping
key with that literal name remains unchanged and is not overwritten.
