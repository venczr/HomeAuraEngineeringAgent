4. ДИАГНОСТИКА HOMEAURA-MANAGER (deep_manager)
   Не более 2 попыток вызова (правило из предыдущих этапов). Цель —
   понять ПОЧЕМУ timeout >90с при живой загруженной модели (ollama ps
   показывал 42%/58% CPU/GPU, 4096 context), а не заставить её отвечать
   быстрее любой ценой. Проверь:
   - размер system-промпта в Modelfile.manager (если существует и
     доступен для чтения);
   - фактическое число офлоуженных на GPU слоёв через `ollama ps`
     подробный вывод / `ollama show homeaura-manager` (если команда
     поддерживается установленной версией 0.32.5);
   - один контрольный вызов с намеренно урезанным промптом
     (например, только `{"status":"ok"}` без system-контекста) и таймаутом
     30с, чтобы отличить "модель в принципе не отвечает" от "модель
     отвечает, но только на очень короткий контекст".
   Зафиксируй результат как ФАКТ/ВЫВОД/РИСК/НЕ ПРОВЕРЕНО. Не меняй
   local_models.yaml на этом шаге — enabled_for_interactive: false для
   deep_manager остаётся, пока диагностика не даст положительный
   результат.

ЦЕЛЕВАЯ АРХИТЕКТУРА (для сверки в разделе 1)
HomeAuraOrchestrator — единственный владелец: основной очереди задач,
SQLite task store, универсальной state machine, RAG, Safety Gate, списка
разрешённых инструментов, Command Runner, маршрутизации локальных
моделей, облачной эскалации, Project Bridge, Codex Relay, Claude adapter,
Telegram approval, аудита, восстановления заданий.
HomeAuraLocalSupervisor — только: наблюдение за процессами, health
monitoring, watchdog, обнаружение зависаний, сбор внешних событий,
уведомления, передача событий в Orchestrator.
HomeAuraEngineeringAgent/tools/local_supervisor — временный прототип
проверки Ollama; не развивать как третью самостоятельную систему.
